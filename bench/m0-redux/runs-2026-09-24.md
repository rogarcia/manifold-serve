## Findings

1. **Pods differ; compare within a pod.** Same prompts, same stack: baseline code c1 62.7 tok/s
   today vs 59.9 on 09-21 (+5%), code c8 377 vs 333 (+13%), and k=5 code c8 speedup 2.40–2.43x vs
   2.16x with the same acceptance length. Candidates: driver (595 vs 580) and host CPU (128 vs
   32 vCPU). Not separated. Acceptance lengths reproduce to ±0.01 (code k=5 5.21/5.21, chat 3.57/3.57).
2. **Repeats.** Seed-to-seed spread 1–3% in tok/s, ±0.05 in acceptance length.
3. **k=7 vs k=5 on code is real** at both concurrencies: +6.6/+7.7/+8.1% at c=1, +5.3/+2.5/+5.6%
   at c=8. The 09-21 p99 TPOT penalty for k=7 at c=8 did not reproduce (10.0–12.7 ms vs
   9.9–11.2 ms). On chat k=7 is 5% slower than k=5 (as on 09-21); on math it is equal.
4. **Sampling (T=0.7, top_p 0.8, top_k 20) costs 3–5% of the MTP speedup**; acceptance length
   drops ~0.1 (code 5.21→5.12, chat 3.57→3.46).
5. **Thinking on lowers acceptance** on GSM8K: 4.83 → 3.91 (k=5), speedup 3.25x → 2.65x.
   Output lengths differ by 28% between baseline and k=5 in this cell (greedy output is not
   bit-identical under spec decode, and long reasoning chains diverge), so compare tok/s only.
6. **Categories (k=5, c=1):** code 5.21 > math 4.83 > translation 4.02 > RAG 3.79 > chat 3.57 >
   summarization 3.37 > QA 3.17 acceptance length; speedup 2.1–3.3x. Translation outputs are
   ~26 tokens, so its tok/s speedup (2.07x) is TTFT-bound; its TPOT ratio is 2.64x.
7. **Acceptance does not fall with input length up to 32k** (SPEED-Bench mixed: 3.93, 4.18,
   3.97, 4.09 at 1k/8k/16k/32k). The TPOT ratio holds or rises (2.53x → 2.93x) because
   baseline TPOT grows with context and MTP's does not. The end-to-end tok/s speedup falls
   (2.66x → 2.16x) only because prefill (3.3 s at 32k) is a larger share of each request.
8. **The TTFT gap is a CUDA-graph effect, not a spec-decode one.** Baseline captures CUDA graphs
   up to 16 tokens (`[1, 2, 4, 8, 16]`); MTP k=5 up to 96 (`[1, 2, 4, 6, 8, 12, …, 96]`), k=7
   up to 128, because each decode step carries k+1 tokens per sequence. Prefills of ~84 tokens
   (chat, math) fit a captured graph under MTP: 36 ms vs 86 ms on baseline. Code prompts (~180
   tokens) fit neither: ~85 ms on both. The baseline could get the same with a larger
   `max_cudagraph_capture_size` (not in the recipe; not tested). On 09-21 the baseline TTFT
   was ~75 ms higher on every cell, which made the gap look larger (170 vs 110 ms).
9. **TRITON_ATTN is faster than FlashInfer on this card for both configs** (baseline +3.4–4.0%).
   At c=1 the MTP speedup ratio is unchanged. At c=8 k=5 gains 16.5% (904 → 1053 tok/s, speedup
   2.40x → 2.68x) with the same acceptance, consistent with the fused multi-step draft path.
   Single run per Triton cell; the three FlashInfer k=5 c8 seeds span 904–937.

## Protocol problems

- **M0 loadgen counted SSE chunks as tokens.** `manifold/loadgen` set `output_tokens` to the
  number of content chunks. Under spec decode a chunk carries several tokens, so tok/s and TPOT
  for MTP were undercounted by roughly the acceptance length. This affects the part2 MTP numbers
  (28 tok/s at 37.6% acceptance, k=3). Fixed: tokens now come from `stream_options.include_usage`;
  the chunk count is kept as `output_chunks`.
- **The loadgen's prompts degenerate on this model.** "Question N about X: tell me one more
  thing." gets an immediate EOS (1 token, empty content) on later turns; once a session has an
  empty turn it tends to stay empty. Empty replies: 11% at 1 req/s, 31% at 2, 51–62% at 4–8.
  The baseline sweep (`results/2026-09-24/sweep/baseline/`) is kept as a record and is not a
  measurement of the server. Item 7 was dropped.
- My first explanation for the TTFT gap (hidden empty chunks under baseline) was wrong; the
  chunk-timing probe (`ttft-probe.jsonl`) ruled it out before the TTFT test found the cause.
